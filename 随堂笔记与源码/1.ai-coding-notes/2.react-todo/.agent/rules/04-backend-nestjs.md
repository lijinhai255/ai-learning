# NestJS 服务端规范

## 脚手架与启动

`apps/api-nest` 以 Nest CLI 生成的工程为基线，保留 `nest-cli.json`、分层编译配置和标准启动入口。新增业务边界优先使用 `pnpm --filter @todo/api-nest exec nest g module <name>`、`nest g controller <name>` 和 `nest g service <name>` 生成骨架，再补充测试与实现。开发、构建、类型检查和单元测试走应用自身脚本，根目录只负责编排。

## 模块设计

每个业务边界使用独立 NestJS module，公开接口通过 module exports 明确暴露。Controller 负责协议适配，Service 负责业务编排，Repository 负责持久化，纯规则放入可独立测试的 domain 函数。模块之间通过接口或应用服务协作，避免循环依赖。

## 输入与输出

所有请求参数、查询、请求体和环境变量均通过 DTO、Pipe 或 schema 校验，并在边界完成类型转换。响应 DTO 明确字段白名单，避免直接返回 ORM 实体。分页、排序、过滤和幂等语义写入 API 契约与测试。

## 错误与可观测性

使用统一异常过滤器将领域错误映射为稳定错误码和 HTTP 状态。日志包含请求标识、模块、耗时和结果，不记录密码、令牌和完整个人数据。外部调用设置超时、重试上限和熔断策略，异常路径提供可定位上下文。

## 数据访问

事务边界由应用服务声明，迁移脚本可重复执行并经过回滚演练。查询避免隐式 N+1，分页使用稳定排序。并发更新通过版本号、唯一约束或幂等键保护，关键写入覆盖冲突测试。

## 安全基线

鉴权和授权在服务端执行，Guard 或 Policy 只负责边界判断，业务服务仍校验资源归属。CORS、限流、请求体大小、头部和依赖漏洞检查纳入部署门禁。敏感配置使用环境变量或密钥服务，仓库仅保留示例值。
