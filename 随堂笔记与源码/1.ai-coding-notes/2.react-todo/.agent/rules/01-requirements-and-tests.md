# 需求拆解与测试先行

## 需求拆解产物

开始编码前，任务记录至少包含以下内容。

1. 背景和用户目标，说明谁在什么场景下需要什么结果。
2. 范围和非目标，列出本次明确处理与刻意排除的内容。
3. 用户场景，使用「给定条件、执行动作、期望结果」描述。
4. 业务规则，覆盖状态转换、权限、校验、幂等、错误和边界。
5. 数据与接口契约，包含字段、类型、必填性、默认值、错误码和兼容策略。
6. 非功能要求，至少评估性能、可访问性、安全、可观测性和可维护性。
7. 验收矩阵，将每条验收条件映射到测试文件、命令和结果证据。

需求有歧义时，优先依据现有产品行为、契约和测试作出最小假设，并在任务记录中标出假设。影响数据模型、权限或公开 API 的歧义需先获得用户决定。

## 测试先行流程

每个需求条目按红、绿、重构推进。

- 红阶段先写失败测试，测试标题描述用户行为而非内部函数名。
- 绿阶段实现满足当前测试的最小逻辑，避免顺手扩展范围。
- 重构阶段消除重复、整理边界和命名，再运行完整门禁。

推荐测试层级如下。

| 层级   | 工具                          | 关注点                                      |
| ------ | ----------------------------- | ------------------------------------------- |
| 单元   | Vitest                        | 纯函数、状态转换、组件交互、NestJS 服务分支 |
| 集成   | Vitest + Supertest 或测试容器 | 模块协作、数据库、HTTP 契约                 |
| 端到端 | Playwright                    | 从浏览器观察的关键用户旅程、跨前后端流程    |
| 契约   | schema 校验与生成测试         | 请求响应兼容、错误结构、版本演进            |

## 用例覆盖

每项功能至少覆盖成功路径、空输入或空状态、边界值、重复操作、失败依赖和权限差异。涉及异步流程时，覆盖加载、成功、失败和重试状态。涉及持久化时，覆盖刷新或重新打开后的恢复行为。

## 测试质量要求

- 测试隔离外部系统，使用工厂和固定时钟，避免依赖执行顺序。
- Mock 只替换边界，不替换待验证的业务逻辑；集成测试保留真实序列化和校验。
- Playwright 使用稳定的可访问名称、角色或 `data-testid`，避免依赖 CSS 层级和固定等待。
- 测试失败信息需能指出场景、输入和期望；禁止吞掉异常。
- 覆盖率作为趋势指标，关键路径以验收矩阵为准。新增分支需补对应行为测试。
