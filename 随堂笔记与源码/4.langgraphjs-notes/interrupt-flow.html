中断与恢复（Human-in-the-loop）流程讲解

LangGraph.js：用 interrupt() 在流程中间暂停，等用户输入后再用 Command({ resume }) 从断点继续
src/6.interrupt/agent.ts

一、整体结构图

左边是图的静态结构（只有一条线），右边是它的运行时序——一次任务被拆成「两次 invoke」，中间夹着一次用户输入。

二、执行时序讲解

  1. 第一次 invoke：agent.invoke({ times: 0, url }, config)。 带上了 config（thread_id: "thread-1"），所以这一次的运行现场会被 MemorySaver 存成检查点。
  2. 跑到中断点：先执行 fetchTool 抓取网页、写 text； 进入 interrutNode 后遇到 interrupt("你满意吗？")，图立即暂停并把该问题抛给调用方， 这次 invoke 就此返回（返回值里带 __interrupt__）。
  3. 终端等待用户输入：这次不写死在代码里，而是用 ask() 阻塞等用户敲键盘。
    • 输入 「是」 → 继续第 4 步；
    • 输入其它（如 「否」）→ 打印「已中断，流程结束。」直接 return，图不再继续。
  4. 第二次 invoke 恢复：agent.invoke(new Command({ resume: answer }), config)。 Command({ resume }) 告诉图「从断点继续，并把 resume 值当作 interrupt() 的返回值」。
  5. 续跑到结束：interrupt() 返回 "是" → 节点 return { approved: "是" } → 边继续到 modelNode → END，第二次 invoke 返回最终状态。
为什么必须传 config + checkpointer：
中断的本质是「把图的状态冻结存盘、之后原样解冻」。没有 MemorySaver 就没有检查点可存； 两次 invoke 必须用同一个 thread_id，否则第二次会被当成一次全新运行，而不是恢复。

六、要点补充

  • interrupt() 是"值"而不是"控制流"：它像函数一样返回，但第一次执行时不会真正返回——而是抛出中断、保存现场；只有 resume 之后，它才带着 resume 值"回过头来"继续执行。
  • resume 值的类型就是你传进去的东西：这里传 answer（字符串）→ interrupt() 返回字符串；若传 true，返回的就是 boolean。
  • 暂停点在节点内部：恢复时，整个 interrutNode 会从头重新执行，但 interrupt() 这一行会直接拿到 resume 值，所以中断之前的副作用需要自己保证幂等。
  • store vs checkpointer：store（InMemoryStore）是跨线程的长期记忆；checkpointer（MemorySaver）是单个线程的运行检查点。中断恢复靠的是后者。
  • 命名小提醒：节点名拼写为 interrutNode（少了一个 p），虽然不影响运行，但容易与变量名混淆，可留意统一。
